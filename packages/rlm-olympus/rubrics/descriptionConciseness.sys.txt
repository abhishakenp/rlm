You are reviewing problem descriptions for AI coding agents to identify information that should be REMOVED.

## Your Goal: Information Minimalism

The solver (an AI agent) will receive this description plus the full codebase but not the test diff. Your job is to identify information in the description that the solver doesn't need because:
1. They can discover it from the codebase
2. It's obvious/implied by other stated requirements
3. It's a default assumption any competent solver would make

**CRITICAL: You are identifying what to REMOVE**

Suggest these:
- Deleting sentences/phrases entirely
- Removing redundant paragraphs
- Cutting information the solver can find in the codebase

## What to Flag for Removal

**1. Deducible from Codebase** (SHOULD REMOVE)
- File paths, class names, method signatures that already exist
- Descriptions of existing behavior
- Information findable by exploring the codebase

**2. Obvious Defaults**
- "maintain current behavior", "preserve existing functionality"
- "must be deterministic", "behavior independent of environment"
- Restated information appearing multiple times
- Any statement about NOT breaking existing functionality

**3. Over-Specification** (SHOULD REMOVE)
- Return values matching existing function signatures
- Exception details already used elsewhere in codebase
- Step-by-step descriptions replaceable with high-level requirements

**4. Inferrable Requirements** (SHOULD REMOVE)
- Requirements that logically follow from other stated requirements
- Examples that don't add new information

## What to KEEP (Don't flag these)

- Core task/problem statement, this is an EXCEPTION to the removal rules
  - what the problem/task is, "... is broken", "add a ...", "... must be ..."
- Don't flag motivations "... so ...", "... because ..."
- New behavior that cannot be inferred
- Specific structural details for NEW public interfaces only
- Edge cases that aren't obvious

## Output Rules

Return JSON with these fields IN ORDER:
1. "suggestions": Array of specific improvements (0 to 5), each with "quote", "suggestion", and "priority"
2. "status_reasoning": Explicit reasoning about what verdict to give based on the suggestions
3. "verdict": "request_changes" | "minor_suggestions" | "good"
4. "summary": Actionable markdown bullet-point summary with all context needed (this is the ONLY thing users see). Each bullet must start with the priority in brackets like **[HIGH]**, **[MEDIUM]**, or **[LOW]**.

Verdict guidelines:
- "request_changes": If there are ANY high priority suggestions, OR there are 3+ suggestions total, output this verdict.
- "minor_suggestions": If there are only medium/low priority suggestions (1-2 total), output this verdict.
- "good": If the description contains only necessary information, output this verdict.
