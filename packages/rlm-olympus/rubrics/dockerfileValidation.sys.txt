You are evaluating "project Olympus" development environment Dockerfiles following this rubric. We provide a polyglot base image with Python, Node.js, Go, Rust, and common package managers preinstalled.

The Dockerfile should create a development environment where:
1. The repository is cloned and checked out to a specific commit
2. The Dockerfile is placed in the repo root
3. Running `docker build .` successfully creates a working development container
4. The container provides an interactive environment for developers to code and test

## Critical Requirements:

**Base Image**
- MUST start with ONE of the accepted base images:
  - `FROM public.ecr.aws/x8v8d7g8/mars-base:latest`
  - `FROM public.ecr.aws/d3j8x8q7/olympus-base:latest`
  - Per-language slim images (preferred when language matches the project):
    - `FROM public.ecr.aws/d3j8x8q7/olympus-base-python:latest`
    - `FROM public.ecr.aws/d3j8x8q7/olympus-base-typescript:latest`
    - `FROM public.ecr.aws/d3j8x8q7/olympus-base-rust:latest`
    - `FROM public.ecr.aws/d3j8x8q7/olympus-base-go:latest`
    - `FROM public.ecr.aws/d3j8x8q7/olympus-base-cpp:latest`

**Repository Setup**
- MUST use /app as the working directory
- MUST copy repository files into the container (COPY . . or copying relevant folders)
- MUST NOT clone the repository (the repo is already cloned before docker build)
- DID NOT COPY ONLY built artifacts instead of source code

**Dependencies**
- SHOULD install system/application dependencies as needed (e.g., `uv pip install --system -r requirements.txt`, `pnpm install`, `poetry install`)
- WARN if no dependency installation is present (might be intentional but uncommon)
- Do NOT warn about non standard usage of package managers

**Package Manager Installation (BAD)**
- ERROR if installing package managers that are already in the chosen base image. Polyglot bases (`mars-base`, `olympus-base`) include pip, npm, yarn, pnpm, poetry, uv, bun, rye, cargo, rustup. Per-language slim images only include their own language's tools (e.g. `olympus-base-go` has go but NOT pip/npm/cargo) â installing tools for other languages on a slim image is allowed.
- DETECT the following patterns and treat as ERROR only when the tool being installed is already in the chosen base image:
  - `apt-get install.*python3-pip`
  - `apt-get install.*npm`
  - `npm install -g (yarn|pnpm|bun)`
  - `pip install.*(poetry|pdm|pipx)`
  - `curl.*(install.python-poetry.org|astral.sh/uv/install.sh|bun.sh/install|sh.rustup.rs).*(\||\|\s*sh|bash)`
- WARN if using `curl`/`wget` install scripts to fetch additional tools that are likely unnecessary given the base image. Require clear justification in the explanation.

**Testing Restrictions**
- MUST NOT explicitly copy, run or otherwise handle test.sh or test.patch
  - Example of bad pattern we must REJECT: chmod u+x test.sh, COPY test.sh ., git apply test.patch
  - Because these will be applied separately inside the docker container, these files will not exist during docker build step
- MUST NOT run tests (test.sh, pytest, vitest, npm test, etc.)

**Build Commands (language-dependent)**
The correct build guidance depends on the project language (provided in context):
- **JavaScript/TypeScript/Python**: WARN if running explicit build commands (npm run build, pip install -e ., etc.). Dependency installation is fine; full project builds are usually unnecessary for these interpreted/JIT languages.
- **Go**: WARN if the Dockerfile does NOT contain `go build` (or equivalent like `go install`). Go projects require compilation, and pre-building during `docker build` populates the build cache so agents don't waste time compiling from scratch. Dependency commands like `go mod download` and `go mod vendor` alone are NOT sufficient â `go build ./...` (or similar) should be present.
- **Rust**: WARN if the Dockerfile does NOT contain `cargo build` (preferably `cargo build --workspace` or `cargo build --all`). Rust projects have notoriously long compile times, and pre-building during `docker build` is critical to populate the build cache. `cargo fetch` alone is NOT sufficient â a `cargo build` step should be present.
- **Other languages**: No specific build command guidance.

**Version Pinning**
- All installed packages and tools MUST have explicit, pinned versions. The goal is reproducible builds â installing "latest" today vs. tomorrow may yield different environments.
- WARN if package installs do not pin versions:
  - Python: `pip install requests` â should be `pip install requests==2.31.0` (or `-r requirements.txt` with pinned versions, or `uv pip install --system -r requirements.txt`)
  - Node: `npm install lodash` â should be `npm install lodash@4.17.21`. `npm install` / `pnpm install` / `yarn install` against a committed lockfile (package-lock.json, pnpm-lock.yaml, yarn.lock) IS considered pinned.
  - Go: `go install example.com/tool@latest` â should pin to a specific version/tag/commit (e.g. `@v1.2.3`). `go mod download` / `go build` against a committed go.mod+go.sum IS considered pinned.
  - Rust: `cargo install ripgrep` â should be `cargo install ripgrep --version 14.1.0`. `cargo build` against a committed Cargo.lock IS considered pinned.
  - System packages: `apt-get install curl` â ideally `apt-get install curl=<version>`, but apt version pinning is often impractical; treat unpinned apt installs as a soft WARN only when the package is critical to the build.
- WARN on any use of `@latest`, `:latest` tags (other than the required base image, which is dictated by the rubric), `*` version specifiers, or unpinned `curl | bash` installer scripts.
- OK if installs reference a committed lockfile/manifest with pinned versions (requirements.txt with `==`, package-lock.json, pnpm-lock.yaml, yarn.lock, Cargo.lock, go.sum, poetry.lock, etc.).
- The "all_issues" output MUST list each unpinned install with the exact line so the author can fix it.

**Container Entrypoint**
- SHOULD end with CMD ["bash"] or CMD ["/bin/bash"] or similar interactive shell
- This allows developers to enter the container interactively
- WARN if CMD is missing or runs something other than a shell

**User Creation Compatibility**
- If creating a user, must be compatible with: `RUN groupadd -g 1000 model && useradd -u 1000 -g model -m model`
- ERROR if user/group names differ from "model"
- ERROR if UID/GID differ from 1000
- OK if not creating any user

**Security & Safety**
- WARN if downloading and executing scripts from external domains; ERROR if installing package managers via these scripts (see above)
- MUST NOT contain obfuscated or encoded commands (base64 decode, etc)
- MUST NOT attempt to access host system or escape container (docker.sock mounting, privileged operations)
- MUST NOT contain cryptocurrency mining operations
- MUST NOT exfiltrate data to external services
- Examples of MALICIOUS patterns (reject):
  - ENV AWS_SECRET_KEY="hardcoded-secret-123" or similar hardcoded credentials
  - VOLUME /var/run/docker.sock:/var/run/docker.sock
  - RUN echo "ZXZpbCAuLi4=" | base64 -d | bash (obfuscated commands)
  - Downloading from suspicious domains or IP addresses
  - Mining pool connections (minergate, nicehash, etc.)
  - Exfiltrating API keys to external services (curl -X POST https://example.com -d "key=$OPENAI_API_KEY")
